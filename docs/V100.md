# Tesla V100 + RTX 4070 Super + 96 GB RAM (this fork)

This fork runs Unsloth's **UD-Q4_K_XL** of Qwen3.8-Flash-Next ([UNSLOTH_Q4.md](UNSLOTH_Q4.md)) on one specific PC:

| | |
| --- | --- |
| GPU 0 | RTX 4070 Super, 12 GB, Ada (sm_89), WDDM (it drives the display) |
| GPU 1 | Tesla V100 PCIe, 32 GB HBM2 (~900 GB/s), Volta (sm_70) |
| CPU | Core i5-13600K: 6 P-cores + 8 E-cores, AVX2 (no AVX-512) |
| RAM | 96 GB DDR5 |
| Toolkit | CUDA 12.9 (CUDA 13 cannot compile for sm_70) |

## Why it should be much faster than upstream

Upstream ran UD-Q4_K_XL on **one GPU** with a RAM budget of RAM − 24 GB (40 GiB on 64 GB). The other ~30 GiB of the
71.7 GiB of experts came from the SSD for every token: 7-8.5 tok/s, and ~550-750 ms of every verify round was SSD
time.

Here both cards share the model by a **layer split**, and the RAM budget mode now works on a split:

- the V100 holds roughly 24-26 GiB of experts, the 4070 Super roughly 5-6 GiB, so ~30 of the 71.7 GiB sit on GPUs;
- the RAM copy holds **only the experts no GPU holds** (~42 GiB), so it fits the 96 GB with room to spare;
- so nothing is read from the SSD while it answers (`file blobs 0` in the log), and the OS file cache keeps
  most of the 28.8 GB PLE table as well.

What is left per token is GPU time on two cards plus the CPU computing the experts no GPU holds. Those are the
coldest ones, so their share of the routed work is well under their ~58% share by count.

**Card order: 4070 Super first (CUDA0), V100 second.** The last stage also carries the output head and the MTP draft
layer (~1 GB), which costs the 32 GB card little and the 12 GB card a lot. The V100 runs without WDDM's per-launch
overhead if it is in TCC mode (the Tesla default on Windows), and `--layer-split auto` gives it the layers its
cache can hold. `tools/v100_bench.py` measures the reverse order too (`v100_first`), along with the V100 alone.

## What changed in the engine

- **V100 (sm_70) correctness.**
  - `qsa_prompt_attn.cu`: the tensor-core prompt attention checked only the compute capability's *major* number,
    so a V100 (7.0) was taken for Turing (7.5) and launched a kernel compiled to `__trap()`: a crash on the first
    long prompt. It now needs 7.5, and Volta keeps the FP32 prompt attention.
  - `prefill/gemm.cu`: the prompt path's BF16 GEMMs fall back to an FP32 kernel, which reads BF16 exactly, on a card
    where cuBLAS has no BF16 GemmEx (it answers NOT_SUPPORTED / ARCH_MISMATCH), instead of exiting.
    `STRATA_BF16_GEMM_FALLBACK=1` forces the kernel, `=0` forbids it.
  - Every other kernel was compiled for sm_70 and audited. cp.async, tf32 / m16n8k* mma and `ldmatrix` are all
    behind guards with Volta fallbacks; shared-memory opt-ins are sized per device (96 KB on V100); `__dp4a` and
    `__nanosleep` exist on sm_70.
- **The RAM-budget mode on a layer split** (`generate.cpp`).
  - `--resident-budget-gib` is no longer refused with `--layer-split`.
  - The later stages' cached experts are passed to the complement planner, so the RAM copy leaves them out.
  - The adaptive tier's swap now copies an evicted expert back from **the card that owns its layer**. Before, it
    always read CUDA0's cache, which would have put wrong bytes into RAM on a split.
  - The exchange buffers are pinned *portable*, so the V100 copies into them by DMA.
  - Under WDDM the RAM copy is locked in RAM rather than page-locked into two GPU contexts (the reason the arena's
    pinning is capped at 8 GiB on Windows splits). `STRATA_ARENA_PIN_GIB=0` allows page-locking again.
- **setup.py**: Volta is admitted without `STRATA_EXPERIMENTAL_SM60=1` (`=0` opts out). The Unsloth model keeps both
  GPUs (`STRATA_BUDGET_ONE_GPU=1` restores the old one-GPU behavior). The engine is compiled locally for
  `sm_70;sm_89` with the CUDA 12.x toolkit (`-DSTRATA_EXPERIMENTAL_SM60=ON`, chosen by setup).
- **The prompt path's MMQ kernels for Q4_K / Q5_K / Q5_1 experts are compiled in but OFF** (`-DSTRATA_MMQ_KQUANTS=ON`,
  added by setup for a Volta build). `prefill_mmq_kquant_test` left output rows unwritten on both cards (first GPU run,
  2026-10-02), so prompts use FP16 dequantize + cuBLAS (measured ~10% slower, known correct) until that is fixed.
  `STRATA_MMQ_KQUANTS=1` in the config's `env` turns them on (bench variant `mmq_kq`).
- **New test** `bf16_gemm_fallback_test` (cuBLAS vs fallback against FP64), and the two tools below.

## Running it

All from the Strata folder. Each step writes a log in the Strata folder.

1. `v100\1_setup_and_build.bat` - **uses no GPU** (safe while another program uses the cards). It finds both
   cards with nvidia-smi, then runs setup with `--setup --build --no-start --family unsloth --model UD-Q4_K_XL
   --gpus <4070S>,<V100> --context 32768 --vision no`. Setup downloads the 111 GB of shards if they are not in
   `Strata-data` yet (`--gguf-dir` uses files you already have), packs, compiles the engine, and writes
   `strata-unsloth-ud-q4_k_xl.json`. The script then compiles the GPU test programs. Log: `v100_setup.log`.
2. `v100\2_gpu_tests.bat` - **uses both GPUs** (~30-40 min). It runs the kernel parity tests on each card alone,
   then `tools/v100_bench.py`: every variant reloads the model and measures decode, 4K/16K prompt speed and a
   greedy coding answer. Logs: `v100_gputest.log`, `v100_bench.log`, `v100_bench.json`.
3. `v100\3_start_server.bat` (or setup's own `run-unsloth-ud-q4_k_xl.bat`) - the server on
   `http://127.0.0.1:8080`.

4. `v100\4_long_context.bat [context]` - rewrites the config for a long context (default 262,144, the model's full
   trained window; setup turns on KV streaming), without compiling, then (after a pause, **both GPUs**, ~45-60 min)
   runs `tools/v100_longbench.py`: prompt reading and writing speed at 32K / 128K / 240K tokens and a needle recall
   test at 240K. Log: `v100_longbench.log`.

5. `v100\5_prompt_chunks.bat` - compiles the changed engine files (no GPU), then (after a pause, **both GPUs**,
   ~25-35 min) runs `tools/v100_prefillbench.py`: 8192-token chunks on both cards against the V100 at 16384 and
   32768, each on a ~16K and a ~120K-token prompt with a code word to find, and a follow-up turn.
   Log: `v100_prefillbench.log`.

After step 2, `START-HERE.bat --calibrate` tunes `--spec-min-p`, `--pcie-frac` and the CPU worker count on this PC
and saves the result in the config.

## Settings worth knowing

| Setting | Default here | Why |
| --- | --- | --- |
| `gpu` / `layer_split` in the config | `[4070S, V100]`, `auto` | auto places the boundary so the two caches hold the most routed mass |
| `--resident-budget-gib` | 71 (RAM − 24, capped at all experts) | a cap: only the ~42 GiB no GPU holds are copied |
| `--max-context` | 32768 | every GB of KV is a GB less of cached experts; the KV is carved per card (each card holds only its layers') |
| `STRATA_SPLIT_MISS_MS` | 190 | the split search's cost of a CPU miss; Q4 experts on this CPU may want ~300 (bench variant `miss300`) |
| `STRATA_KQ256=1` | off | multi-token AVX2 kernels for the CPU's Q4_K/Q5_1/Q8_0 experts (bit-exact; bench variant `kq256`) |
| `--pool-affinity auto --pool-workers 11` | all cores | keep the E-cores out of the expert pool (bench variant `pcores`) |
| `STRATA_SPLIT_OWN=1` | off | each card keeps its own prompt buffers: faster prompts, different resident set (bench variant `own_buffers`) |

**Windows commit charge:** the ~42 GiB RAM copy, plus every GPU allocation of a WDDM card, counts against RAM +
page file. Keep the page file "System managed" (see DETAILS.md, troubleshooting).

## First GPU run (2026-10-02)

- Every kernel parity test passes on both cards, V100 included, except `prefill_mmq_kquant_test` (both cards; the MMQ
  prompt kernels are therefore off by default, above). cuBLAS has a BF16 GEMM on the V100 (5 TFLOP/s), so the fallback
  kernel is not needed there; it passes too.
- The greedy coding answer was token-for-token the same in all 8 benchmark variants, including the V100 alone.
- Bug found and fixed: on a split the RAM copy was ranked by CUDA0's share of the profile only, so it held just CUDA0's
  layers' experts (20.3 GiB of the 42 GiB) and the V100's layers read ~7,450 experts from the files. The V100 alone
  (no split, everything in RAM) was the fastest variant: 31 tok/s against 9-12 tok/s for the split.
- The CPU pool on the P-cores (and their SMT siblings) without the E-cores was 3x faster than all cores in that run
  (28.7 vs 9.3 tok/s), with file reads in the path; it is measured again after the fix.
- **The V100 runs at PCIe 3.0 x4** (3.3 GB/s measured by the engine; the 4070 Super has 23.8 GB/s). Decode barely
  crosses PCIe, but prompts stream the experts no GPU holds to the card that runs the layer, so long prompts are limited
  by that link on the V100's layers. A slot wired to the CPU (x8 or x16) would help prompts directly.

## Second GPU run (2026-10-02, after the RAM-copy fix)

The RAM copy now holds all 41.8 GiB of the experts no GPU holds; no expert is read from the files (`file blobs 0`).
Greedy decode, 192 tokens, median of 6 (3 prompts x 2), 32K context:

| Variant | Decode tok/s | Prompt 4K / 16K tok/s |
| --- | ---: | ---: |
| 4070S + V100, all cores (setup's config) | 41.0 | 219 / 461 |
| **4070S + V100, P-cores + SMT (11 workers)** | **43.3** | 220 / 451 |
| 4070S + V100, P-cores only (5 workers) | 40.6 | 218 / 456 |
| V100 + 4070S (V100 first) | 34.8 | 220 / 373 |
| V100 + 4070S, P-cores + SMT | 37.4 | 227 / 370 |
| V100 alone | 33.3 | 186 / 380 |
| (upstream: one 12 GB GPU, 64 GB RAM) | 7-8.5 | 41 / 160 |

- The default is now the 4070 Super first with `--pool-affinity auto --pool-workers 11` (`tools/v100_setup.py`
  writes it into the config after setup). The second run of each prompt is ~50% faster than the first: the expert
  cache adapts to the conversation.
- Every greedy answer is correct code; the P-core variant's differs from token 19 (another expert placement, a
  near-tie), the rest are identical.
- Prompts are the weak spot (~460 tok/s at 16K, ~10% lower than run 1 with the MMQ kernels off): the V100's PCIe 3.0
  x4 link and its FP32 prompt attention.

## Long-context run (2026-10-02, 262,144 context, KV streaming 32,768 cells per layer in VRAM)

| Prompt | Read speed | Read time | Writing speed |
| --- | ---: | ---: | ---: |
| 31,059 tokens | 481 tok/s | 65 s | 38.4 tok/s |
| 121,651 tokens | 580 tok/s | 210 s | 35.0 tok/s |
| 234,221 tokens | 545 tok/s | 430 s | 30.6 tok/s |

- Needle recall at 234K tokens: found at 90%, 50% and 10% depth. The summaries are accurate.
- KV streaming: 91-95% of the K/V block reads hit VRAM during the answer, so writing slows only ~20% from 32K to 240K.
- Reading speed barely depends on the length (580 vs 545), so the prompt attention is not the limit yet. Per 8192-token
  chunk the prompt path streams every expert the card does not hold to the card that runs its layer: ~27 GB to the
  V100 (~8 s over PCIe 3.0 x4) and ~25 GB to the 4070 Super (~1 s). That is roughly half of the ~15 s per chunk.
- The chunk stays at 8192 because the 4070 Super's cache (1,798 slots) cannot lend more: 8192 already borrows 1,374
  of them. The V100 could lend a 32,768-token chunk's buffers (~5,500 of its 8,323 slots).
- The borrowed slots' experts are in neither the GPU cache nor the RAM copy, so 2,761 of them are read back from the
  GGUF files after every prompt (~8 GB, mostly the OS file cache).
- Prompt cache: a checkpoint every 16,384 fresh tokens, 4 kept. The needle runs (a change in the middle) reused only
  the first 16,384 tokens; a follow-up that appends to the conversation reuses everything up to the last turn.

## Per-card prompt chunks (2026-10-02)

The prompt is read in chunks; for every chunk each card streams the experts of its layers that it does not hold.
The chunk used to be one size for all cards: the largest every card's expert cache can lend the buffers for, which
on this PC is the 4070 Super's 8192. The V100's ~27 GB stream per chunk was then paid every 8192 tokens.

Now, with `--prefill auto:16384` or `auto:32768`, each later card in the split takes the largest chunk (up to that
size) that **its own** cache can lend, under the same rules (at most 85% of its slots, 128 left). The 4070 Super
keeps reading 8192-token chunks; `Prefill::run` gathers its chunks' rows in the hand-off buffer and passes them to
the V100 in one piece. Every layer is causal in the positions, so the state after the prompt is the same; only the
expert stream and the GEMM batch sizes change.

- The pinned hand-off buffers grow to the V100's chunk (40 KB per token: 2 x 1.3 GB at 32768) on the first long
  prompt. If they cannot be pinned, the hand-offs stay at the old size.
- Mid-prompt checkpoints are taken at the V100's chunk boundaries (the earlier card saves its part only there).
- A start that does not fit falls back to one chunk for every card before trying smaller chunks.
- `STRATA_SPLIT_STAGE_CHUNKS=0` turns it off. `STRATA_PREFILL_TIMING=1` now names the card and the chunk.
- After every request the engine log has one line per card: its tokens, chunks, time, experts streamed (by DMA) and
  host staging time, plus the time spent reading experts from the model files.
